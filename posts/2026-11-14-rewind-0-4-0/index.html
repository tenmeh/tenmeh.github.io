rewind 0.4.0: only what the page can put back

R
Shiny
packages

rewind 0.4.0 is on CRAN. It stops recording inputs that an undo cannot put back, such as the hover of a plot, and adds a way to load a saved view without making it a step.

Author

Tanmay Chanda

Published

14 November 2026

rewind 0.4.0 is on CRAN. It is the biggest update since the first release. Most of it came from one question: why does an undo sometimes seem to do nothing?

My first post explains what rewind does. In short, it adds undo and redo to a Shiny app with one call, rewind_enable(). It records the inputs as the user works, and puts them back at an undo.

Only what the page can put back

By default, rewind now records only the inputs that the page can put back.

Before 0.4.0, rewind recorded every input of the session. Some inputs have nothing on the page to put back. The hover of a plot is the clearest case. plotOutput(hover = "plot_hover") sends the position of the pointer as an input, but no element on the page holds that value.

So each pause of the pointer over the plot became a step. The rail filled with plot_hover, and an undo of such a step changed nothing that the user could see:

The same was true of the values that DT keeps, such as _rows_current and _state, and of a plot’s click, dblclick and brush.

The fix asks the browser. Each input that the page can put back has a Shiny input binding on an element: a select, a slider, a text box. The browser now reports which inputs have one, and rewind records only those. Inputs that are only sent from JavaScript, such as the hover of a plot, have no binding, so they are left out.

The report arrives after the page has loaded. Until it does, rewind records every input, as before. That is also what happens in testServer(), which has no browser.

There are two ways to change the default:

  • A list in inputs is used as it is. Name an input there to record it anyway: rewind_enable(inputs = c("region", "year", "plot_brush")).
  • rewind_exclude() leaves inputs out, from anywhere in the server. More on that below.

This is a change of behaviour. An app that relied on the old default to record a value with no binding now needs to name it in inputs. I think such apps are rare, because an undo of those values did nothing on the page.

Why did an undo skip this input?

The new rewind_status() answers that in one call. It lists what rewind records, and gives each other input the reason it is left out:

rewind_status()$captured   # c("region", "year")
rewind_status()$skipped    # c(plot_hover = "cannot be restored by the page",
                           #   pw = "password field")

The reasons are "excluded", "password field", "not in inputs", "cannot be restored by the page", "action button", "file upload" and "NULL value". The list also holds the groups registered with rewind_track(), and the size of the history and the current position.

It depends on the inputs, so it works well in a debug panel:

output$status <- renderPrint(rewind_status())

rewind_exclude() is the other half. It leaves inputs out of the history, at any time, and from inside a module:

mod_filters_server <- function(id) {
  moduleServer(id, function(input, output, session) {
    rewind_exclude("search")   # the module's own name, not "filters-search"
  })
}

It works like shiny::setBookmarkExclude(). A second call adds to the list, and an input that the history already holds is removed from it.

A view that is not a step

A saved view is a set of input values that the app loads in one go: from a bookmark, from a list of saved filters, or from the defaults of a user. Loading a view is not something the user did by hand, so it should not be a step.

The new rewind_unrecorded() runs a block of code whose changes are not a step:

observeEvent(input$load_view, {
  rewind_unrecorded({
    updateSelectInput(session, "region", selected = "East")
    updateSliderInput(session, "year", value = 2020)
  })
})

The changes become part of the current state instead. An undo never goes back across them:

Why a pause does not work

The help of rewind_pause() used to suggest a pause and a resume around code like this. That does not work, and finding out why was the most useful part of this release for me.

rewind records in its own observer. That observer depends on every input, so it runs after the observer that made the change. By then, the resume has already run. The probe I wrote recorded the change as an ordinary step.

There is a second problem: update*Input() sends a message to the browser. The new value comes back as an input later, after the observer has ended.

So rewind_unrecorded() does not pause anything. After the block, it keeps a short window open, twice the grouping period by default. A change that arrives in that window replaces the current state, and does not make a new step. A change from the user that was still waiting becomes its own step first, so the loaded view never swallows it.

Names a person reads

The rail and rewind_diff() used the input ID as the label of a step. An ID such as year is fine. An ID such as sel_trt_arm is not something a user should read.

rewind_enable() now takes labels:

rewind_enable(labels = c(region = "Region", trt = "Treatment arm"))

The rail shows the labels, and rewind_diff() has a new label column. It is the last column, so code that picks the six columns of 0.3.0 by position still gets the same ones.

The smaller things

  • Every argument is checked, with a message that names it. Some wrong values used to be accepted, and did the wrong thing with no message: shortcuts = "yes" turned the shortcuts off, depth = 2.5 became 2, and rewind_jump(1.9) moved to position 1.
  • A typo gives a warning. A name in inputs that the page does not have, or a name in rewind_track(fields = ) that the values do not have, used to record nothing, with no message.
  • A busy input no longer holds back every step. The grouping period started again whenever any input changed, also an input that is not recorded. A plot hover thus held back every step until the pointer stopped.
  • Password fields are never kept in the history. A passwordInput() sends a plain string, so rewind recorded it like any text box, and rewind_diff() could show it. The browser now reports which fields are passwords, and rewind leaves them out, even when inputs names them.
  • rewind_enable(c("region", "year")) put the names into session, the first argument, and failed with “$ operator is invalid for atomic vectors”. It now says that session must be a Shiny session, and points to inputs = c(...).
  • rewind_example() runs the demo app. It replaces shiny::runApp(system.file("examples/demo", package = "rewind")).
  • The help of rewind_track() has a new section on environments and R6 objects. rewind keeps those by reference, so a change inside such an object is not a step, and an undo cannot bring back its old contents. The section shows how to change a copy instead.
  • The help of rewind_enable() has a new section on text inputs: why slow typing can give several steps, and how textInput(updateOn = "blur") gives one step for each edit.
